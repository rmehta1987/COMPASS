# COMPASS — Embedding Model Evaluation Results

Aggregated results for all retrieval experiments run against the COMPASS survey-codebook
variable-retrieval benchmark. Every number below is read directly from the JSON reports
in `out/` (produced by `src/compass_score.py`, `src/train.py`, and `src/finalize.py`); the
source file is cited on every row so any number here can be traced back to its run.

## 1. Task and dataset

**Task.** Given a short natural-language search request (e.g. `"exogenous hormone
medication"`), retrieve the correct survey-dictionary variable ("target") from a fixed
corpus by cosine similarity between a query embedding and pre-computed target embeddings
(argmax over the corpus — a single-relevant-item retrieval/selection task, not
multi-relevance ranking).

**Target corpus** (`out/targets_full.json`, `dictionary_version_hash = 3dc8415eccfe`):

| | |
|---|---|
| Selection targets | 1,353 |
| Distinct constructs (questions) | 1,066 |
| Multi-option targets (siblings under one question) | 343 |
| Folded-family targets (one target represents a roster asked once per person/entity) | 119 |
| Singleton targets | 1,234 |
| Largest construct (most sibling options) | 49 |

Built by `build.py` from `dictionary.json`, stripping piped Qualtrics identifiers and
excluding direct identifiers and free-text companion fields (`src/compass_build.py` /
`build.py`).

**Evaluation fixture** (`retrieval_queries.json`, schema `retrieval_eval_queries/1`):
224 queries, generated 2026-08-31 by `claude-haiku-4-5` (4 phrasings/item, batched 8,
`seed=20260831`), gold rule = roster-normalised text equality.

> **Declared bias** (from the fixture's own `KNOWN_BIAS` field): queries were generated by
> a model that saw the gold item's wording, with "do not copy distinctive phrases" as an
> instruction but no enforced leakage check. This favours semantic retrieval over lexical
> and inflates absolute recall. **Treat cross-model comparisons as indicative and any
> single model's absolute recall as an upper bound**, not a ground-truth production number.

**Training pairs** (`out/training_pairs.json`): 13,528 synthetic `(query, target)` pairs
covering all 1,353 targets (0 missing), generated by the same generator model
(`claude-haiku-4-5`) driven through the Claude Code CLI with `--allowed-tools ''`
(no network, no tool access) — declared explicitly in `src/gen_training.py` so the
generator could not leak outside information into the training set.

## 2. Metrics — what each column means

All metrics are computed in `src/compass_score.py::evaluate` / `subset_stats`, over the
224-row fixture (unless noted) with 0 unreachable rows.

| Metric | Definition |
|---|---|
| **R@k** (`@1/@5/@10/@25/@50`) | Fraction of queries where the gold target's rank ≤ k, by cosine similarity. R@1 is top-1 selection accuracy — the deployed operating point (argmax). |
| **rank p50/p90/max** | Median / 90th-percentile / worst rank of the gold target across all 224 queries — the tail, not just the mean. |
| **Singleton R@1** | R@1 restricted to targets with no folding and no siblings (n=168) — the "easy" case. |
| **Folded-family R@1** | R@1 restricted to targets that collapse a per-person/per-entity roster into one target (n=56) — tests whether the model correctly picks the folded representative over a near-identical un-folded phrasing. |
| **Near-duplicate R@1** (and its ratio to overall R@1) | R@1 restricted to gold targets that have sibling options under the *same* question stem (n=76, `gold_multi_option`) — this is the **discrimination / constraint metric**: it isolates cases where the wrong answer is lexically almost the query's paraphrase but semantically the wrong *option* (e.g. "sibling breast cancer" vs "sibling lung cancer"). A ratio < 1 means the model is disproportionately worse exactly where option-level discrimination matters. |
| **Wrong-construct / right-construct-wrong-option** (of top-1 errors) | Error-type decomposition, i.e. the retrieval **false-positive breakdown**: *wrong-construct* = the model returned an entirely different survey question (coarse failure); *right-construct-wrong-option* = it found the right question but picked the wrong sibling (fine-grained, near-duplicate failure). Reported as count/total-errors and as a fraction. |
| **Sibling cosine p50/p90** (`within_construct_cosine`) | Document-side cosine similarity between sibling target embeddings under the same construct. High values (→1.0) mean the encoder barely separates distinct options belonging to the same question — a direct, label-free signal of a model's option-discrimination ceiling, independent of the query set. |
| **query ms/row, encode s** | Cost: mean per-query encode latency and total corpus (target) encode wall-clock, on the device used for that scoring run (CPU unless noted). |

**Reading the frozen results:** `mxbai-embed-large-v1` leads on every R@k cut and is the

near-duplicate/option-level distinctions than on the benchmark overall. `gte-mbert` has
the most lopsided error profile of any model evaluated (136/137 = 99.3% of its errors are
wrong-construct, essentially never confusing sibling options) but also the worst

folding and option separation. `qwen3-06b`'s near-duplicate ratio (0.632) is the weakest
of the frozen set even though its overall R@1 ties `bge-small`.

per-step batch of documents): 3.6 GB at `n-neg=0` → 14.1 GB at `n-neg=4` → 24.6 GB at
`n-neg=8` for `bge-small`, which is also why train wall-clock roughly quadruples from
`nn0` (~110s) to `nn8` (~850–980s) at fixed epoch count. `bge-small`'s checkpoint has no

GPU cap and peak-memory logging were added between that run and the rest of the sweep —
`--max-gpu-gb`/`peak_gpu_gb` are absent only from `bge-small_nn0_t0.05/compass_train_meta.json`).

`bge-small`'s final training loss climbs monotonically with temperature at fixed `n-neg`
(0.22 → 0.40 → 0.76 → 1.19 for t=0.05→0.10→0.15→0.20 at nn0) — expected, since a higher
temperature flattens the softmax and raises the achievable minimum cross-entropy — so
final loss is **not** comparable across temperatures as a proxy for retrieval quality;
`t=0.10`'s higher loss (0.3975) than `t=0.05`'s (0.22) still scores better on R@1 (§4
table). `embgemma` and `mxbai` converge to much lower absolute loss (0.05–0.09) than
`bge-small` at the same `t=0.05/0.10`, consistent with their larger capacity, but this
does not translate into higher R@1 than fine-tuned `bge-small` (§4 table) — again,
cross-model loss values are not a valid proxy for the retrieval metrics in this report.

**Fine-tuning vs. frozen, same model.** `bge-small` R@1 rises from 0.375 (frozen) to
0.567 (best fine-tune, +19.2 pts / +51% relative); sibling-cosine p50 drops from
0.9099 → 0.3394, i.e. fine-tuning makes sibling-option embeddings dramatically more
separable, not just marginally. `mxbai-l1` rises from 0.469 → 0.545 (+7.6 pts) and
`embeddinggemma-300m` from 0.371 → 0.504 (+13.3 pts). **The best fine-tuned `bge-small`
(33M params) outperforms every frozen model tested, including `mxbai-l1` (335M) and
`qwen35-08b` (752M)** on R@1, at roughly 1/10 and 1/23 the parameter count respectively,
and at 2.94ms/query vs. their 32.4ms and 139.8ms.

**Hyperparameter pattern (bge-small):** `t=0.10` dominates across `nn` ∈ {0,4,8}
(0.567/0.540/0.536); moving to `t=0.05` or `t=0.15`/`0.20` costs 3–8 R@1 points at every
`nn`. Adding mined hard negatives (`nn=4` or `nn=8`) did **not** help at the best
temperature — `nn=0` (in-batch negatives only) is the top config — though at `t=0.05`,
`nn=8` (0.500) beats `nn=0` (0.509) only marginally and `nn=4` (0.473) is worse, so the
negative-mining benefit is inconsistent rather than absent. `t=0.02` (extremely sharp,
`nn=4`) is the clear failure mode: sibling cosine p50 stays at 0.7248 — barely improved
from the frozen 0.91 baseline — meaning that temperature under-trained option separation
even though the loss still converged.

## 5. Experiment 3 — Target-text rendering ablation ("gate" runs)

Tests how the *document side* text is constructed from `(stem, option)` before encoding
(`src/compass_score.py::target_text`), holding the model (`bge-small`, frozen) and a fixed

(n_targets = 1,241, n_rows_scored = 208 for all four rows.)

Duplicating the stem as a stand-in when a target has no option (`stem_option_dup`) is
worth **+8.2 R@1 points** over the otherwise-identical `stem_option` rendering, and every
alternative rendering underperforms it — this is why `stem_option_dup` is the convention
used as the default document text for every other table in this report. The gap is
concentrated at R@1/R@5 and narrows by R@50, i.e. the rendering choice mainly affects
top-of-list precision, not whether the gold target is retrievable at all.

already drops (0.799 → 0.786). Below 512 dims R@1 degrades steadily and R@5 drops sharply
(0.665 at d=256) — MRL truncation is viable only down to ~768 dims for this task, well
short of the aggressive 128-dim compression sometimes advertised for this model family.
The reported latencies here are noisy relative to the frozen full-dim run (same model,
similar or higher ms/row at 512–256 than at full) — read the MRL cost column as indicative
only, not as a clean speed/accuracy frontier, since these runs share a log (`out/sweep*.log`)
with other concurrent scoring jobs rather than isolated timing.

## 7. Deployment parity checks (`src/finalize.py`, `out/finalize.log`)

For the four checkpoints selected for shipping, `finalize.py` re-encodes the full corpus
on CPU (the deployment device), independently re-encodes on GPU, and asserts the two give
identical top-1 selections row-by-row — because small numeric differences between devices
can specifically flip the argmax on the near-duplicate pairs this benchmark is designed to
stress (see module docstring).

The fine-tuned `bge-small` checkpoint has exactly one GPU/CPU top-1 disagreement, at row
107 (query *"primary method used to get to work"*, CPU picks `m1:Q4.1`, GPU picks
`m2:Q25.1`) — a floating-point boundary case (`max |vec delta| gpu-cpu` ≈ 4.06e-7), not a
correctness bug, but it means CPU- and GPU-served results for this specific query can
diverge in production and should be noted if this checkpoint ships. Isolated per-query
latency scales roughly with embedding dimension and encoder size: 384-dim `bge-small` is
~6x faster per query than 1024-dim `mxbai` (17.8ms vs 107.2ms) and the `mxbai`/`embgemma`
checkpoints are ~10x the disk size of `bge-small`'s.

## 9. Caveats that apply to every number above

1. **Fixture leakage bias** (declared in `retrieval_queries.json.KNOWN_BIAS`, §1): the
   224-query eval set was generated by a model that saw the gold wording. Absolute R@k
   values are an upper bound; relative model-vs-model orderings are more trustworthy than
   the absolute numbers.
2. **Training/eval register match**: the same generator (`claude-haiku-4-5`) wrote both the
   224-query fixture and the 13,528 training pairs (`src/gen_training.py` docstring
   states this explicitly as "a real cost, declared rather than hidden") — fine-tuned
   scores in §4 are flattered by this alignment relative to how a differently-phrased,
   real-world query stream would score.
3. **Small eval set**: 224 rows total, and subset breakdowns (singleton n=168, folded
   n=56, near-dup n=76) are small enough that single-row flips move R@1 by 0.4–1.8 points.
4. `arctic-m2` and `biolord` are configured in code (`src/compass_score.py::MODELS`) but
   are not present in any table here — the former failed to load (§3), the latter was
   never run.
5. §6's MRL cost figures are drawn from a shared sweep log and are not isolated timing
   runs; treat them as directional only.
